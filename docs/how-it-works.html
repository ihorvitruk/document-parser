Document Parser: how it works

A guided tour of the system for someone seeing it for the first time: what runs where, what happens to a document from upload to result, and why it is built this way.

In one sentence. A user uploads PDFs; the API immediately says "accepted" and puts each document in a queue; background workers take documents from the queue, extract the text of every page (with PyPDF or an LLM) and ask Gemini for a summary; the website shows the results as they become ready.

Terms used below

API
The web server (FastAPI) that the browser talks to. It never does the slow work itself.
Worker
A background program that takes documents from the queue and processes them. Several run at once.
Queue
A list of jobs waiting to be done. Here it is a Redis Stream.
Consumer group
A Redis feature that hands each queue entry to exactly one worker of a team.
Acknowledge (ack)
A worker telling Redis "this job is finished". Unacknowledged jobs are not forgotten.
Parser
The method that turns a PDF into text: PyPDF, Gemini or GPT-5 Mini.

3. Where things are stored

There is no database. Everything the system remembers is in Redis, and it expires after 24 hours (configurable).

Redis keyTypeHolds
doc:<id>hashOne document: file name, parser, status, error, summary, page count, pages (as JSON), timestamps. Expires after the TTL.
docs:indexsorted setDocument ids ordered by creation time, so the list can be shown newest first.
docs:streamstreamThe queue: one entry per document waiting to be processed, holding just the id.
group docs:workersconsumer groupTracks which worker received which entry, how long ago, and how many times.

The uploaded PDF itself is a file on a volume shared by the API and the workers (/data/uploads/<id>.pdf); the queue entry carries only the id, never the file. The file is deleted as soon as the document finishes.

4. The code, module by module

Module (backend/app/)Responsibility
api/routes.py, api/main.pyThe HTTP endpoints and app start-up. Thin: validate, call the helpers below, answer.
uploads.pySaves an upload to disk; checks it is a real PDF (by its first bytes, not its name) and within the size limit.
storage.pyThe only place that reads and writes documents in Redis. Includes a safe update that never recreates an expired document.
queue.pyThe only place that talks to the stream: read a new job, take over an abandoned one, acknowledge.
models.py, errors.py, config.pyData shapes, the two error kinds (temporary and permanent), and all settings read from environment variables.
parsers/pypdf_parser.pyPlain text per page with PyPDF.
parsers/chunked.pyLogic shared by the LLM parsers: cut the PDF into chunks, send chunks in parallel (limited), check the answers, renumber pages.
parsers/gemini_parser.py, openai_parser.pyHow to ask each model: request format, response format. Everything else is shared.
parsers/registry.pyWhich parsers exist, which are usable (is the API key set?), and creation of each parser once.
llm/gemini.py, openai_client.pyOne call to a model with a time limit, error classification (temporary or permanent) and retries.
llm/retry.pyThe retry rule: repeat only temporary errors, with growing pauses, a bounded number of times.
llm/summarizer.pyBuilds the summary request and calls Gemini.
worker/main.pyThe worker loop: take over abandoned jobs, otherwise wait for new ones; heartbeat while a job runs; clean shutdown.
worker/processor.pyProcesses one document from start to a final status. Safe to run twice for the same document.

The frontend (frontend/src/) is small: App.tsx polls the API and owns the list, UploadForm.tsx handles file picking, drag and drop and parser choice, DocumentCard.tsx shows one document (status, summary, collapsible pages), and api.ts is the only file that calls the backend.

Why the LLM parsers send chunks

Each answer is validated: the model must return exactly as many pages as were sent, as JSON in a fixed shape. An answer that does not match counts as a temporary error and the request is repeated.

6. When things go wrong

A worker dies in the middle of a job

If the same document keeps killing its workers, Redis's delivery counter exceeds MAX_DELIVERIES (3) and the document is marked failed instead of looping forever.

What happens on each kind of failure

SituationWhat the system doesUser sees
Upload is not a PDF, too large, or has an unavailable parserRejects the whole request before anything is saved or queued.An error under the upload form, naming the file.
PDF is corrupt, password-protected or emptyPermanent error: no retry.Status Failed with the reason.
LLM rate limit, server error, network problem, timeoutTemporary error: up to 3 attempts with pauses of about 2 s and 8 s.Normal result if a retry works; otherwise a clear message including "gave up after 3 attempts".
Wrong API key, rejected request, no OpenAI creditPermanent error: no retry.The reason, for example "Gemini rejected the API key".
Parsing worked but the summary failedKeeps the pages, records why the summary is missing.Status Done, pages shown, a notice instead of the summary.
Scanned PDF with PyPDFParses to empty pages; skips the summary call.Done, with "no extractable text" and a hint to use an LLM parser.
A worker dies mid-jobAnother worker takes the job over (see above).Nothing; the document just finishes slightly later.
Unexpected bug while processing one documentMarks that document failed; the worker keeps running.Failed, with a generic message (internals are not exposed).

7. Decisions and trade-offs

DecisionWhy
Redis Streams with a consumer group as the queueRequired by the task; it also gives "each job to exactly one worker", persistence, and takeover of abandoned jobs without extra code.
The API never parses; it only queuesUploads stay fast and the API stays responsive however slow the parsing is. Workers scale independently.
Document and queue entry written in one transactionA document can never exist without being queued, or the other way round.
Only the id goes through the queue; the file sits on a shared volumeKeeps queue entries tiny and avoids storing PDFs in memory-limited Redis.
Partial result when the summary failsDelivering the parsed pages is worth more than rejecting everything because one optional step failed.
Temporary and permanent errors handled differentlyRetrying a rate limit makes sense; retrying a wrong API key never does.
Summary always by Gemini, never selectableThe task states it; the parser, by contrast, is the user's choice.
Parsers and LLM clients behind small interfacesAdding GPT-5 Mini needed one new parser class and one client; the queue, worker and API did not change.
Polling instead of websocketsSimplest thing that works; the document list is small and requests are cheap.
No databaseThe task is about asynchronous processing; Redis alone is enough for results that expire. A production system would store results in a database and keep Redis only as the queue.
